# 数据转换前准备与调试说明

本文用于告诉导师：运行和调试 AMASS 数据转换前需要准备什么、文件放在哪里，以及应该从哪些函数开始看。

## 需要准备的内容

| 内容 | 用途 | 当前仓库使用位置 |
|---|---|---|
| AMASS 原始动作 | 提供人体姿态、root 平移和原始帧率 | `dataset/AMASS` |
| SMPL-H 人体模型 | 把 AMASS 参数转换成 24 关节位置 | `dataset/body_models` |
| `body_fbx_rest.json` | 对齐 Python 骨架和 Unity `body.fbx` 静止姿态 | Unity 工程的 `Models/DiffusionPoser` 目录 |
| Python 环境 | 提供 numpy、scipy、torch、smplx 等依赖 | Conda 环境 `diffusionposer5070` |
| 当前仓库代码 | 执行转换和检查输出 | `DiffusionPoser` 仓库 |

当前机器上这些内容已经准备完成并通过读取检查。

## 当前机器的实际位置

大数据放在仓库同级的 `artifactStore`，仓库内通过目录联接使用，避免复制大文件：

```text
DiffusionPoser/
├─ dataset/
│  ├─ AMASS/         -> ../artifactStore/DiffusionPoser/active/raw/AMASS
│  └─ body_models/   -> ../artifactStore/DiffusionPoser/active/raw/body_models
└─ ../SIGGRAPH2024Unity/Assets/Projects/RealtimePose/Models/DiffusionPoser/
   └─ body_fbx_rest.json
```

当前检查结果：

- 转换器可读取 14,096 个 AMASS 动作；
- `SMPLH_FEMALE.npz`、`SMPLH_MALE.npz`、`SMPLH_NEUTRAL.npz` 齐全；
- `body_fbx_rest.json` 包含并通过 24 骨骼顺序、parent 和 rest transform 校验；
- SMPL-H 模型可以由 `smplx` 正常加载。

`dataset/` 已被 Git 忽略，因此这些目录联接和原始数据不会随代码提交。导师如果换电脑调试，需要重新建立目录联接，或在命令中传入实际绝对路径。

## AMASS 文件最低要求

转换器递归读取 `dataset/AMASS/**/*.npz`。每个动作至少需要：

| 字段 | 要求 |
|---|---|
| `poses` | `[T,D]`，至少 66 维；当前 SMPL-H 数据通常是 156 维 |
| `trans` | `[T,3]`，帧数必须和 `poses` 相同 |
| `mocap_framerate` | 原始动作帧率 |

下面两个字段可以缺省：

- `betas`：缺失时使用零 shape 参数；
- `gender`：缺失或无法识别时使用 `neutral`。

当前转换器不读取 `dmpls`。文件名为 `shape.npz` 的文件不会被当作动作。

## SMPL-H 模型要求

当前实际使用：

```text
dataset/body_models/
├─ SMPLH_FEMALE.npz
├─ SMPLH_MALE.npz
└─ SMPLH_NEUTRAL.npz
```

转换器根据 AMASS 文件中的 `gender` 选择模型；male/female 加载失败时会尝试回退到 neutral。

## Unity rest pose 要求

默认文件：

```text
../SIGGRAPH2024Unity/Assets/Projects/RealtimePose/Models/DiffusionPoser/body_fbx_rest.json
```

该文件需要包含：

- 24 个 `boneNames`；
- 24 个 `parents`；
- 24 个 `restLocalPositions`；
- 24 个 `restLocalRotations`；
- 6 个 `trackerJointIndices`。

它必须由当前 Unity 工程和当前 `body.fbx` 导出。骨骼顺序或 parent 不一致时，不应手工修改 JSON，应回到 Unity 重新导出。

## 数据转换入口

主入口：

```text
data_converter/amass_to_realtime_pose.py:593  main()
```

调用顺序：

```text
main()
└─ convert_one_motion()

```

## 算法调试重点

导师调试转换算法时，主要看下面这些文件和函数：

| 文件/函数 | 负责内容 | 主要检查内容 |
|---|---|---|
| `data_converter/amass_to_realtime_pose.py:593` | 转换主入口 | 输入目录、参数和动作数量 |
| `data_converter/amass_smpl_utils.py:91` | 读取 AMASS | `poses`、`trans`、fps、gender |
| `data_converter/amass_smpl_utils.py:182` | 重采样 | 帧数、旋转连续性、首尾帧 |
| `data_converter/amass_smpl_utils.py:232` | 加载人体模型 | 是否进入 SMPL-H 分支、性别是否正确 |
| `data_converter/amass_smpl_utils.py:265` | SMPL-H 前向 | 输出是否为 `[T,24,3]` 关节位置 |
| `data_converter/amass_smpl_utils.py:407` | AMASS → Unity 坐标 | 人物是否出现倒置或坐标轴错误 |
| `data_loaders/body_fbx_kinematics.py:124` | 转换 body.fbx local delta | root 和普通关节的局部旋转是否正确 |
| `data_loaders/body_fbx_kinematics.py:232` | root-y0 FK | pelvis 是否能恢复到原世界位置 |
| `data_converter/amass_to_realtime_pose.py:161` | 生成最终 source 字段 | 所有字段形状和数值是否正常 |

转换算法的主要数据变化：

```text
AMASS poses/trans
  → 重采样到 60 Hz
  → SMPL-H 24 关节位置与旋转
  → AMASS 坐标转 Unity 坐标
  → root yaw、root position、pelvis height 分解
  → body.fbx local delta rotation6D
  → 目标骨架 FK
  → 6 个 Tracker 和静止概率
```

关键形状：

| 数据 | 形状 |
|---|---|
| SMPL-H 关节位置 | `[T,24,3]` |
| body pose rotation6D | `[T,144]` |
| 目标骨架世界位置 | `[T,24,3]` |
| Tracker 世界位置 | `[T,6,3]` |
| Tracker 世界旋转 | `[T,6,6]` |

调试时最重要的检查：

- 中间数组不能出现 NaN/Inf；
- rotation matrix 应保持正交且行列式接近 1；
- `root_pos_world[:,1]` 应为 0；
- FK 后的 pelvis 应与转换前的 pelvis 世界位置一致；
- Tracker 位置应等于对应的 6 个关节位置；
- 改变 SMPL `batch_size` 不应改变转换结果。

## 单动作调试命令

第一次调试只处理一个动作，并关闭多进程，确保断点能够命中：

```powershell
conda run -n diffusionposer5070 python -m data_converter.amass_to_realtime_pose `
  --amass_dir dataset/AMASS `
  --smpl_model_dir dataset/body_models `
  --body_fbx_rest_json ../SIGGRAPH2024Unity/Assets/Projects/RealtimePose/Models/DiffusionPoser/body_fbx_rest.json `
  --output_dir output/debug_realtime_pose_source `
  --target_fps 60 `
  --batch_size 64 `
  --num_workers 1 `
  --limit 1 `
  --overwrite
```

注意：

- 调试时保持 `--num_workers 1`，否则核心转换在子进程中执行；
- `--overwrite` 只对独立的 debug 输出目录使用；
- 完整转换时移除 `--limit 1`，再增加 `--num_workers`；
- 首次排错不要使用 `--allow_partial`。

## 数据转换之后的完整调用流程

整个 Python 主链路如下：

```text
AMASS + SMPL-H + body_fbx_rest.json
  → ① Source 转换
  → ② Task Store 生成
  → ③ Normalizer 计算
  → ④ 模型训练
  → ⑤ 单样本或长序列推理
  → ⑥ 指标评估
  → ⑦ Unity/Sentis 导出
```

各阶段的输入、输出和入口：

| 阶段 | 入口模块 | 输入 | 主要输出 |
|---|---|---|---|
| ① Source 转换 | `data_converter.amass_to_realtime_pose` | AMASS、SMPL-H、Unity rest pose | 60 Hz realtime source `.npz`、`manifest.jsonl` |
| ② Task 生成 | `data_loaders.generate_realtime_pose_tasks` | Source 目录、train/test split | 未归一化 mmap Task Store |
| ③ Normalizer | `data_loaders.compute_realtime_pose_normalizer` | train Task Store | pose、Tracker、Head path 的统计文件 |
| ④ 训练 | `train.train_diffusionposer` | Task Store、Normalizer | `model*.pt`、可选 `ema*.pt`、训练日志 |
| ⑤ 推理 | `sample.reconstruct_stream` | test Task、checkpoint、Normalizer | 单样本重建 `.npz` |
| ⑤ 长序列推理 | `sample.evaluate_longseq_eval_set` | 长序列评估集、checkpoint、Normalizer | 每条序列的 rollout `.npz` 和汇总 |
| ⑥ 评估 | `eval.evaluate_realtime_pose` | 推理产生的 `.npz` | `eval_summary.json` |
| ⑦ 导出 | `export.write_unity_runtime_assets`、`export.export_sentis_denoiser` | Normalizer、checkpoint | Unity runtime JSON、ONNX/Sentis 模型 |

### ① Source 转换

该阶段就是前文说明的数据转换：

```text
原始 AMASS 动作 [T,D]
  → 60 Hz realtime source
  → body_pose [T,144]、Tracker、root、joints 等字段
```

输出目录保持 AMASS 的相对目录结构，并生成 `manifest.jsonl`。只有 source 转换成功后才能生成 Task Store。

### ② 生成 Task Store

入口：

```text
data_loaders/generate_realtime_pose_tasks.py:720  main()
```

常用命令：

```powershell
conda run -n diffusionposer5070 python -m data_loaders.generate_realtime_pose_tasks `
  --source_dir dataset/AMASS_realtime_pose_body_fbx_local_pelvis_residual_root_y0_stationary5_60hz `
  --output_dir dataset/AMASS_realtime_pose_144d_pelvis_residual_root_y0_stationary5_60hz_tasks `
  --split_dir data_loaders/splits `
  --splits train test `
  --base_windows_per_source 20 `
  --shard_size 4096 `
  --seed 10
```

这一阶段会：

1. 根据 split 文件选择 train/test source；
2. 从每个 source 中抽取固定长度的 61 帧密集窗口；
3. 从 60 帧历史中选择 10 个历史锚点，再加当前帧组成 11 帧模型窗口；
4. 为每个基础窗口保存五套 Tracker 场景；
5. 写成可 mmap 读取的 `.npy` shard。

核心输出包括：

```text
pose_window_clean          [M,11,144]
tracker_window_continuous  [M,11,6,9]
head_path_window           [M,11,5]
configured/measured_valid  [M,5,61,6]
```

`M` 是 task 数量。该阶段的数据仍未归一化。

主要调试位置：

- `generate_realtime_pose_tasks.py:111`：Task 生成总流程；
- `generate_realtime_pose_tasks.py:135`：生成计划和参数检查；
- `generate_realtime_pose_tasks.py:488`：构建单条 Task Store 记录；
- `realtime_pose_validation.py`：Task 字段形状校验。

### ③ 计算 Normalizer

入口：

```text
data_loaders/compute_realtime_pose_normalizer.py:124  main()
```

常用命令：

```powershell
conda run -n diffusionposer5070 python -m data_loaders.compute_realtime_pose_normalizer `
  --task_dir dataset/AMASS_realtime_pose_144d_pelvis_residual_root_y0_stationary5_60hz_tasks `
  --output_dir dataset/meta_AMASS_realtime_pose_144d_pelvis_residual_root_y0_stationary5_60hz `
  --split train
```

该阶段只使用 train split，逐 shard 合并 Task 生成时保存的统计量，输出：

```text
pose_mean.pt / pose_scale.pt
tracker_mean.pt / tracker_std.pt
head_path_xz_mean.pt / head_path_xz_std.pt
head_height_mean.pt / head_height_std.pt
normalizer_meta.json
```

Normalizer 必须和当前 Task Store 配套使用。训练和推理应使用同一套统计文件。

主要调试位置：

- `compute_realtime_pose_normalizer.py:30`：遍历 shard 并合并统计量；
- `utils/normalizer.py`：实际归一化和反归一化逻辑。

### ④ 模型训练

入口：

```text
train/train_diffusionposer.py:26  main()
```

主要调用关系：

```text
train_diffusionposer.main()
├─ get_dataset_loader()
│  └─ RealtimePoseTaskDataset.__getitem__()
├─ create_model_and_diffusion()
└─ TrainLoop.run_loop()
   └─ compute_losses()
      └─ GaussianDiffusion.training_losses()
         └─ RealtimePoseSpatioTemporalDiT.forward()
```

训练时 Dataset 返回 `x: [B,11,144]`，但 diffusion 只处理当前帧：

```text
x_start = x[:, -1]  # [B,144]
```

前 10 个历史姿态作为条件，不进入 diffusion Markov chain。模型另外读取 Tracker、Head path、历史置信度和窗口有效 mask。

常用训练命令：

```powershell
conda run -n diffusionposer5070 python -m train.train_diffusionposer `
  --model_arch spatiotemporal_dit `
  --data_dir dataset/AMASS_realtime_pose_144d_pelvis_residual_root_y0_stationary5_60hz_tasks `
  --data_split train `
  --normalizer_dir dataset/meta_AMASS_realtime_pose_144d_pelvis_residual_root_y0_stationary5_60hz `
  --save_dir runs/your_experiment `
  --scenario_weights 1 1 1 1 1
```

训练算法的重要断点：

- `data_loaders/realtime_pose_dataset.py:131`：一个样本如何组装；
- `train/training_loop.py:233`：训练循环；
- `train/training_loop.py:389`：当前帧 diffusion target 和条件；
- `diffusion/gaussian_diffusion.py:1465`：加噪、模型调用和各项 loss；
- `model/realtime_pose_spatiotemporal_dit.py:400`：模型前向。

### ⑤ 推理与重建

单样本快速调试入口：

```text
sample/reconstruct_stream.py:273  main()
```

它会读取 test Task 的一个样本，加载 checkpoint，调用：

```text
reconstruct_batch()
  → build_sampling_model_kwargs()
  → diffusion.projected_ddim_sample_loop()
  → save_reconstruction()
```

输出保存为 `realtime_pose_reconstruction.npz`。该入口适合检查模型是否能加载、DDIM 是否正常运行以及输出字段是否完整。

真正的实时逐帧逻辑位于：

```text
sample/realtime_pose_runtime.py
└─ RealtimePoseRuntime.step()
   └─ step_realtime_pose_batch()
```

长序列评估使用 `sample.evaluate_longseq_eval_set`，从冷启动开始逐帧把上一帧预测写回历史，比单个 Task 重建更接近实际运行状态。

### ⑥ 指标评估

入口：

```text
eval/evaluate_realtime_pose.py:415  main()
```

调用关系：

```text
main()
├─ evaluate_file()  # 每个 .npz
└─ summarize()      # 汇总所有序列
```

常用命令：

```powershell
conda run -n diffusionposer5070 python -m eval.evaluate_realtime_pose `
  --input_dir output/realtime_pose_result `
  --output_json output/realtime_pose_result/eval_summary.json
```

评估包含姿态旋转误差、MPJPE、速度/加速度误差、jitter、Tracker 约束误差、root 误差、接触准确率和 foot slide 等指标。

### ⑦ Unity 与 Sentis 导出

最后两个主要入口：

```text
export.write_unity_runtime_assets
export.export_sentis_denoiser
```

前者把 normalizer 和 runtime 配置写成 Unity 使用的 JSON；后者加载 checkpoint 并导出 denoiser ONNX/Sentis 资产。导出必须使用与训练 checkpoint 配套的 normalizer 和模型参数。

## 一站式流水线与逐阶段调试

`scripts.run_realtime_pose_pipeline` 可以依次执行：

```text
convert → tasks → normalizer → train
```

它不包含采样、评估和导出。

该脚本通过子进程调用四个阶段。正式批处理可以使用它；导师需要下断点时，建议直接启动正在检查的模块，例如 `train.train_diffusionposer` 或 `data_loaders.generate_realtime_pose_tasks`，避免断点落在子进程中无法命中。

可以先用 `--dry_run` 查看它将执行的命令：

```powershell
conda run -n diffusionposer5070 python -m scripts.run_realtime_pose_pipeline `
  --save_dir runs/pipeline_check `
  --dry_run
```
